# 插件系统架构

给**改宿主**的人看。写插件的人看[插件开发指南](./插件开发指南.md)就够了。

这份文档讲的是：宿主怎么把「一个目录」变成「一个能用的插件」，每个模块负责什么，
以及**为什么这么设计**——尤其是不这么写会踩的坑。

---

## 1. 全貌

```
                    ┌──────────────────── src/shared/  ← 契约只有一份
                    │  plugin.js  清单 + 窗口规格
                    │  panel.js   界面积木
                    └───────────▲──────────▲───────────┘
                                │          │
        ┌───────────────────────┘          └────────────────────┐
        │                                                    │
┌───────┴────────┐   ┌────────────┐   ┌──────────────┐  ┌─────┴──────┐
│ loader.js      │   │ host.js    │   │ window.js    │  │ renderer/  │
│ 发现 + 加载    │→  │ 注册 + ctx │   │ 窗口 + 壳    │  │ ui/        │
└────────────────┘   └─────┬──────┘   └──────┬───────┘  │ blocks.js  │
                             │                 │          │ pluginPage │
                        ┌────┴─────────────────┴───┐      │ theme.css  │
                        │      surface.js          │      └────────────┘
                        │  界面路由：谁挂着、推给谁  │
                        └────────────┬─────────────┘
                                     │
                    ┌────────────────┴─────────────────┐
                    │                                  │
            ┌───────┴────────┐              ┌──────────┴────────┐
            │ 面板工作台      │              │ 独立窗口 / 小部件  │
            │（panel.cjs）   │              │（plugin.cjs）     │
            └────────────────┘              └───────────────────┘
```

**分界线**：`src/shared/` 是主进程与渲染层**都要用**的东西，只定义一次，两边都从这里取。
`src/main/plugins/` 只在主进程跑，`src/renderer/ui/` 只在渲染进程跑。

---

## 2. 契约：`src/shared/plugin.js`

**唯一定义**。宿主与插件作者对「一个插件长什么样」的理解必须一致，
所以只有一份定义——改它要想到两边。

| 导出 | 是什么 |
|---|---|
| `PLUGIN_ID_RE` | id 的正则：小写字母、数字、连字符，1–64 字符 |
| `PLUGIN_WINDOW_LIMITS` | 窗口尺寸的上下限（200×120 到 1200×900） |
| `MIN_PLUGIN_REFRESH_MS` | 刷新周期的下限（500ms）——太密的轮询会把 CPU 跑满 |
| `validateManifest(raw)` | 校验清单。**返回 `{ok, value, errors}`，不抛异常** |
| `defaultWindowSpec(manifest)` | 合成默认窗口规格 |
| `resolveWindowSpec(manifest, mode)` | 按形态取出窗口规格（`window` 段 / `widget` 段） |
| `canDetach(manifest)` | 能不能分离出去 |
| `hasWidget(manifest)` | 有没有小部件形态 |
| `isSafeRelativePath(p)` | 相对路径不能越出插件目录 |

清单校验**返回错误列表而不是抛异常**：一个插件的清单坏了，
不该把整个发现流程带崩——记一行日志，跳过它，其余插件照常可用。

### 为什么「目录名必须等于 id」

插件的页面是按 URL 提供的（`app://…/plugins/<id>/page.html`）。
id 与目录名对不上时，URL 与磁盘接不上——页面装进去是 404 或者空白。
所以在发现阶段就拒掉，而不是等到渲染时才炸。

## 3. 发现与加载：`loader.js`

```
plugins/<id>/plugin.json     ← 内置插件（<项目>/plugins）
<userData>/plugins/<id>/     ← 用户插件
```

流程：

1. `discoverPlugins(roots)` 扫每个根目录的子目录（跳过 `.` 开头的）。
2. 每个子目录读 `plugin.json` → `validateManifest()` → **id 必须等于目录名**。
3. `dedupeById()` 去重：**用户目录的盖掉内置的**（用户明确装了一个同名插件，那是他的选择）。
4. `loadPluginFactory(record)` 用动态 `import()` 加载入口，取 `mod.default`。

**加载一个插件失败只影响它自己**：清单坏了、入口抛错，记一行日志，其余插件照常可用。

### 用户插件目录里的 ESM 标记

`host.js` 会往 `<userData>/plugins/` 写一个 `{"type":"module"}` 的 `package.json`——
userData 下没有 package.json，Node 会把 `.js` 当 CommonJS，插件里那句 `export default`
就成了语法错误，而报错信息（`Unexpected token 'export'`）完全指不出真正的原因。

**只在目录里真的有东西时才写**；用户自己已经放了 package.json 的不动它。

## 4. 注册与生命周期：`host.js`

宿主做三件事：**发现**（loader）、**注册**（把清单交给面板去搜索、把页面交给面板去画）、
**开窗**（window.js）。

### ctx

插件**不知道宿主的存在**。它拿到的是一个上下文（ctx），里面只有它该用到的东西——
这样同一个插件实现既能被面板调用，也能被自己的窗口调用，两条路共用一份实现。

```js
{
  plugin: { id, manifest, dir, source },
  assistant,        // 助理总控（待办/提醒/番茄钟/天气/剪贴板/对话）
  openSettings,     // 打开设置窗口
  update,           // (page) => void：异步动作完成后再刷一次面板
  ui,               // 界面积木（makePage / textBlock / …）
  host: {
    listAll, setEnabled, isEnabled,
    openWindow, closeWindow,
    onSurfaceChange,  // (pluginId, open) => void
  },
}
```

`ctx.update` 存在的理由：天气查询要联网，返回之前页面已经画出来了，
结果到了要再刷一次——但动作返回的页面是**动作发生时**算出来的。

`ctx.host.onSurfaceChange` 存在的理由：插件需要知道「我的界面现在开着吗」。
录屏的快捷键只在界面开着时才注册——一个常驻抢键的录屏插件是很讨人厌的。

### 实例 API 与调用时机

| 方法 | 谁调 | 返回 |
|---|---|---|
| `page(ctx)` | 面板要显示插件 | `Page` / `Promise<Page>`；`null` = **关掉面板** |
| `action(ctx, actionId, value)` | 用户在积木界面上动了 | 新的 `Page`；`undefined` = 插件自己刷了 |
| `meta(ctx)` | **插件有自己的页面**时 | `{title?, subtitle?, status?}` |
| `data(ctx)` | 自带页面打开时 | 任意数据 |
| `tick(ctx)` | 每 `refreshMs` 一次 | 任意数据 |
| `act(ctx, actionId, payload)` | 自带页面里的动作 | 任意数据 |

**`meta()` 与 `page()` 的分工**：插件有自己的页面时，界面是插件自己画的，宿主**不重画**——
它只取 `meta()` 给的标题那几个字段。所以带页面时 `meta()` 要写得**便宜**：
别在里面去列系统窗口，那一下要几百毫秒。

`page()` 返回 `null` 是「关掉面板」，不是「画个空页面」——想画空界面用 `emptyBlock`。

### 页面 URL 与「文件在不在」

`pageUrlOf(id)` 查磁盘上的真实路径（`record.dir` + 相对路径），
返回 `app://…/plugins/<id>/<page>?plugin=<id>`，**文件不在就给空串**。

调用方据此**退回积木界面**——插件照样能用，不会白屏。
所以清单里写了 `page` 但文件被删了，`page()` 仍然是必需的（退回去要靠它画）。

URL **带缓存**：查盘要 `statSync`，而插件清单**每次刷新都会重建**
（面板打开、开关了插件……）——清单里带上页面地址就意味着每次刷新都要 statSync 一遍。
缓存按插件 id 存，插件清单变了就整个丢掉。

## 5. 界面路由：`surface.js`

一个插件的界面可以同时挂在好几处：面板工作台一份，独立窗口一份。
这一层管三件事：

1. **谁挂着**：哪个插件的界面挂在哪些地方；
2. **推给谁**：周期数据送到**所有**挂着的地方（两处看到的数据必须一致）；
3. **什么时候推**：tick 定时器**第一个 surface 挂上来时起，最后一个摘掉时停**——
   界面都没了还按秒推，那是白烧 CPU。

这一层**不碰 Electron**：surface 自己知道怎么把数据送出去（`deliver(kind, payload)`），
路由只管「该送给谁」。

### 推什么

由插件的形态决定（宿主知道）：

- **自带页面**的插件 → 推**数据**（插件自己的 `tick()`）。插件没写 `tick()` 就没有推送。
- **声明式界面**的插件 → 推**重算过的页面**（`page()`）。它的界面是宿主画的，
  要动起来就得重算一次——番茄钟的倒计时就靠它。

两种形态**周期一样**（清单里的 `refreshMs`），要的东西不一样。

### 信封

宿主推给界面的东西**一律包成 `{pluginId, data}`**：
面板可能在两个插件之间来回切，收到的数据得带得清是给谁的。

**各 surface 不拆包**——拆包的是宿主壳（`plugin-window/main.js`）与插件页面助手（`pluginPage.js`）。

一个插件**只有一个 tick 定时器**，不是每个界面一个。

## 6. 窗口与小部件：`window.js`

两种「脱离面板」的形态：

- **独立窗口**（`window`）：自己的窗口，能调整大小、能置顶、能拖到别处；
- **桌面小部件**（`widget`）：无边框、透明、常驻桌面。

**两种形态用的是同一个窗口实例**：切形态就是改窗口的样式与尺寸，重新加载页面。
（`switchMode()` 是**重建**窗口——透明与否、尺寸、置顶规则都不一样。）

**置顶状态不跟着带过去**：小部件永远置顶，把它带成独立窗口的话，
用户会得到一个莫名其妙压着别人的窗口。

### 壳 + iframe

**独立窗口永远是壳**：上面是宿主画的标题栏与窗口按钮（置顶 / 变小 / 关闭），
下面要么是插件自带的页面（装在 `<iframe>` 里），要么是宿主的积木界面。

装进 iframe 而不是直接替换整个窗口：这样**面板工作台与独立窗口结构完全相同**，
只有容器宽度不同——同一份页面两处用，界面天然是一套。

**小部件是例外**：它的页面**原样加载**（带 preload），壳不参与，页面没了就是它自己的事。

### 两个坑

**`win.webContents.id` 要在窗口销毁前存下来。**
不能等到 `'closed'` 里再读 `win.webContents.id`：那时窗口已经销毁了，
那个属性读起来会把**主进程整个冻住**（窗口关不掉、程序退不出去——
表现为「点了退出，程序却不退」）。所以在 `createWindow()` 里读一次存下来。

**`ready-to-show` 要先挂再 `loadURL`。**
页面可能秒开，顺序反了窗口就永远不显示（`show()` 那一行没人调）。

### 退出

`destroyAll()` 直接 `destroy()` 掉所有插件窗口，**绕开 Electron 的正常退出流程**
（`app.quit()` → 逐个关窗口在插件窗口上会卡住，退不出去，进程一直活着；
E2E 里表现为 `app.close()` 永远不返回）。

### 一个插件只能有一个窗口

窗口控制器是「一个插件一个窗口」，`window` 与 `widget` 互斥。
需要**同时开好几个窗口**（录屏的捕获页、选区遮罩、控制条、工作台要一起开着），
就得自己 `new BrowserWindow()`——这时要自己写窗口管理与 preload。
`plugins/screen-recorder/lib/windows.js` 是一个完整的例子。

## 7. 两条 IPC 通道

插件窗口用 `plugin.cjs`，面板用 `panel.cjs`。**两份 preload 不共用**——
插件只需要「显示什么」「用户按了什么」和「控制我这个窗口」，
不该拿到桌宠自己的能力（`moveWindowBy` / `saveSettings` …）。

### 插件窗口（`plugin.cjs` → `window.plugin`）

| 方向 | 通道 | 说明 |
|---|---|---|
| 主 → 渲染 | `plugin:page` | 声明式页面描述 |
| 主 → 渲染 | `plugin:data` | 自带页面的首份数据 |
| 主 → 渲染 | `plugin:tick` | 自带页面的周期数据 |
| 渲染 → 主 | `plugin:ready` | 页面就绪（send）——主进程收到才推数据 |
| 渲染 → 主 | `plugin:data` | 要数据（invoke） |
| 渲染 → 主 | `plugin:act` | 自带页面的动作（invoke） |
| 渲染 → 主 | `plugin:action` | 声明式页面的动作（invoke） |
| 渲染 → 主 | `plugin:window:state` / `:alwaysOnTop` / `:mode` / `:close` | 窗口控制 |

主进程靠 `byContents`（`webContents.id` → pluginId）认出 IPC 是哪个窗口发来的。

### 面板（`panel.cjs` → `window.panel`）

面板那侧多了一层 `surface`：

```
window.panel.surface = {
  data:   () => invoke('panel:surface:data'),
  onData: (cb) => …,     // 主 → 渲染：'panel:surface:data'
  onTick: (cb) => …,     // 主 → 渲染：'panel:surface:tick'
  act:    (actionId, payload) => invoke('panel:surface:act'),
  action: (actionId, value)    => invoke('panel:surface:action'),
}
```

**与插件壳上的 `window.plugin` 同名同形**：插件页面不该知道自己身处面板还是独立窗口
（见 `pluginPage.js` 的 `findApi()`：`window.plugin` → `parent.plugin` → `parent.panel.surface`）。

**三个会返回值的接口，返回的都是「裸值」**——与插件壳那边一致。
（**推送**那条路不一样：推上来的都包成 `{pluginId, data}`。）

### 首份数据要走广播

窗口的 `onReady()` 里，首份数据走 `surfaces.broadcast()` 而不是只发给窗口——
面板那边开着同一个插件时，那边也得有一份。只送窗口的话，面板就少了一份。

### 订阅者要能补发

插件页面在 iframe 里，要等**加载完**才跑脚本、才订阅 `onData`——
而宿主在打开插件的那一刻就把数据推过来了（那时 iframe 还没就位）。
推送不排队，所以 `panel.cjs` 里留了一份 `pendingData`，
`onData` 订阅时补发给**当前插件**的那份（按插件 id 存，留着上一个插件的数据给下一个看就是串台了）。

## 8. 设计取舍

| 决定 | 代价 | 为什么 |
|---|---|---|
| 插件跑在主进程，**没有沙箱** | 一个插件能改坏整个应用 | 插件要碰 Electron（窗口、快捷键、屏幕捕获），沙箱化等于重写一套 API。用户插件是用户自己装的东西 |
| 页面用 **URL + iframe** 提供 | 跨进程通信要走 postMessage / IPC | 页面是普通网页，能用自己的框架、自己的构建流程 |
| 清单与规格**只有一份定义** | `src/shared/` 成了两边都要 import 的模块 | 两边对「插件长什么样」的理解必须一致。写两份就一定会漂 |
| **用户插件盖掉内置的** | 内置插件可能被用户悄悄替换 | 用户明确装了一个同名插件，那是他的选择。日志里留痕，方便查「内置的那个怎么不灵了」 |
| 插件加载失败**只影响它自己** | 可能有一个插件悄悄不可用 | 清单坏了不该拖垮整个应用。日志里有一行 |
| 声明式界面用**描述**而不是命令 | 界面表达力受限 | 宿主要能把同一份描述画在面板和独立窗口两处。复杂的东西让插件自己写页面 |
| 一个插件**一个窗口** | 需要多窗口的插件得自己开窗口 | 窗口生命周期、置顶、退出清理都很麻烦，一个插件一个最容易管。需要多的自己写（screen-recorder 就是） |

## 9. 当前的局限

写下来是为了让人知道边界在哪，不是待办清单。

1. **一个插件只能一个窗口。** 需要同时开多个窗口（录屏的捕获页 + 遮罩 + 控制条 + 工作台）
   只能自己 `new BrowserWindow()`，自己写 preload 与 IPC——`plugins/screen-recorder/lib/windows.js`
   重复了 323 行宿主已有的机制。
2. **窗口与自带页面的 API 是两套。** 独立窗口用 `bindSurface()`，小部件用裸 `window.plugin`。
   同一个插件既有 `window` 段页面又有 `widget` 段页面，就是两套心智模型。
3. **`refreshMs` 对两种形态是同一个周期**，但要的东西不一样（数据 vs 页面）。
4. **自带页面那套目前没有正式插件在用**——只有 E2E 的固件在用 `window.page`、`act`、
   `ctx.host.onSurfaceChange`。它经过了设计，但还没被真实的插件检验过。
5. **插件没有 `ctx.store`**——持久化配置得自己写（录屏自己写了 `lib/config.js`，
   原子写盘 + 规整坏值）。
6. **插件没有 `ctx.hotkey`**——全局快捷键得自己 `import { globalShortcut } from 'electron'`。
