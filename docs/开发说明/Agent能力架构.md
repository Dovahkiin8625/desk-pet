# Agent 能力架构

给**改宿主**的人看：你要动 agent（调工具、操作本机、后台任务）。

这份文档讲的是：桌宠的 agent 怎么跑、一次请求从头到尾经过哪些地方，
以及**为什么这么设计**——尤其是不这么写会踩的坑。

---

## 1. 一个 agent，两处运行

**只有一个 agent。** 以前分成两个：交互层（只说话，两步）与执行层（干活，二十步）。
分成两份的代价：

- 两套提示词，同一件事在两个地方是两种做法；
- 前台没有工具，任何需要一点数据的事都得派单——慢；
- 派单要把请求压成一段说明交给后台——**有损，而且没人发现派歪了**。

现在合成一份：同一个后端（`src/main/assistant/chat/agent.js`）在前台与后台跑。
**前台与后台的差别只有三处**：

| | 前台（用户等着） | 后台（没人等着） |
|---|---|---|
| 步数上限 | 3 | 走设置里的 `agent.maxSteps` |
| 步数用尽时 | **交给后台继续做** | 让模型总结一次 |
| 工具带回的那句话 | **算这一轮的最终答复** | 喂回模型继续干活 |

其余完全一样：同一份系统提示词、同一套工具、同一个审批闸门、同一份记录。

```bash
用户 ──▶ 前台 agent ──┬─ 做完了 ──▶ 一句话给用户
                     │
                     └─ 做不完 / 说了要做却没动手
                            │
                            ▼
                      带着这段对话交给后台 ──▶ 做完了 ──▶ 结果按模板送达
```

## 2. 工具从哪来

一轮的工具是**合并**出来的，不是替换：

```
工具表 = 注册表里的全部工具（fs.* / 插件的工具 / skill.read …）
       + 这一轮多带的（task.run / task.cancel / task.steer / task.delete）
```

- **注册表**：`src/main/assistant/agent/tools/registry.js`。
- **这一轮多带的**：前台多带任务工具（管得住后台那些事），后台不带。

「只聊天」模式（`agent.dispatch === 'off'`）下，**注册表的工具一个都不带**——
桌宠不查本机、不翻文件、不跑命令。

`tools` 也可以传函数：后端调用它时会把「当前这段对话」交给它。
任务工具要靠这个把对话原样交出去（见第 3 节）。

---

## 3. 交出去：带着对话继续

**交出去的是当前这段对话，不是模型重写的一段说明。**

差别很大：用户说的原话、已经查到的结果、模型的理解，全都原样带过去。
后台接着干就行，一个字都不用重写——重写就是有损，有损就会派歪，派歪了没人发现。

两条路都会走到后台：

1. **模型自己交**（正常路径）：调 `task.run`，写清**目标**（goal）与
   **做完的标准**（done_when）。标准是「准」的来源：没有它，「做完了」只是模型自己说了算。
2. **后端替它交**（兜底）：步数用尽，或者**说了要做却一个工具都没调**。
   后者是最伤信任的一种失败——用户以为桌宠在忙，其实什么都没发生。

兜底只发生一次：模型只回一句空话时，后端先提醒它一次
（追加一句「现在就用工具去做」），还是不动才交出去。

**已经交出去过的不再交第二次**：那是派两遍，后台会把同一件事做两回。
靠工具自己声明 `handsOver` 来认。

### 对话要修成能直接发出去的样子

交出去的时候，对话可能正停在半截上——assistant 说了要调两个工具，结果只回来一个。
那样发出去，接口直接 400（`tool_calls` 没有对应的结果）。

`safeConvo()`（`agent/loop.js`）修这个：找到最后一条带 `tool_calls` 的 assistant 消息，
它的每个调用都得有对应的 tool 结果，缺了就从它那里截断。

## 4. 送达契约：结果 + 模板

干活的那层交出的是**结构化结果**，送达路径用**模板**把它变成一句话：

```js
{ ok, title, summary, reason, facts, evidence, taskId }
```

- **失败也有话说**（`没能做完：…`）：用户需要知道这件事没做成，
  否则他会一直等着一个不会来的结果。
- **内部黑话漏不出去**：失败原因过一遍 `userReason()`，工具名、绝对路径、多行日志都不留。
- **不值得打扰的不弹气泡**：做完了但没什么可说的（`做完了`），只写记录。
- **值得打扰的常驻**：它可能等用户回来才看得到——六秒就没了的结果，等于没送到。

---

## 5. 审批

一套闸门（`agent/approval.js`），**每处运行各一个**（前台一个、每个后台任务一个）：
「自动」是任务级的。

三个按钮不对称，是故意的：**允许**（这一次）/ **拒绝**（喂回模型，让它换条路）/
**自动**（本任务内同风险等级全放行）/ **取消**（真的把任务停掉）。

「没等到确认」与「已拒绝」必须分开：用户没点过按钮的事，不能记成他拒绝了。

## 6. 文件地图

```
src/main/assistant/
  chat/agent.js        唯一的后端（前台后台共用）
  chat/prompt.js       普通对话的提示词 + 流式拆分
  chat/caller.js       请求体怎么拼（只有这一份）
  layer/foreground.js  前台这一轮：什么时候退回普通对话
  layer/promise.js     认「我要去做某件事」那句话
  layer/speech.js      答复出站前的最后一道过滤器
  agent/loop.js        多步循环 + safeConvo
  agent/prompt.js      agent 的系统提示词 + 上下文压缩
  agent/result.js      结果结构化 + 送达模板
  agent/tasks.js       任务中枢（提交 / 取消 / 归档 / 追加要求）
  agent/approval.js    审批闸门
  agent/record.js      聊天记录的七种分类
  agent/tools/         工具（注册表、内置、任务、技能）
```

## 7. 改代码前要知道的几件事

- **提示词只有一份**（`agent/prompt.js`）。分叉了，同一件事在两个地方就是两种做法。
- **答复不许出现工具名与内部黑话**：提示词是第一道防线，`sanitizeSpeech()` 是第二道。
- **每个 `tool_call` 都要有一条 `role:'tool'` 的消息**——少一条，接口就 400。
- **工具出错不终止任务**：错误要喂回模型，模型才能换条路。
- **上下文压缩的单位是「轮」**（assistant 带 tool_calls + 后面连续的 tool 消息）：
  只丢 tool 消息会让接口报错。
- **插件的工具不归宿主管**：插件自己的代码在 `plugins/<id>/` 里，
  宿主只提供注册表与运行时。
