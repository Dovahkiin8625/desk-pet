# 桌宠交互层与后台任务层 · 重新分工

> 日期：2026-11-11
> 状态：待评审
> 范围：`src/main/assistant/layer/`、`src/main/assistant/agent/`、`src/main/assistant/index.js`、`src/settings/`、`plugins/chat-history/`、`plugins/tasks/`
> 取代：`2026-11-08-two-layer-agent-design.md` 的 §4（交互层）与 §5（执行层）；交互层那部分作废，后台任务层那部分保留并按本文 §5 调整。

---

## 1. 为什么要改

现在的交互层有五个毛病，都是「桌宠不像桌宠」或者「不够快」：

1. **它自己什么都会干**。挂着 10 个工具（时钟、读文件、列目录、能力清单，外加 6 个任务管理工具），系统提示词里还贴着一份插件名与工具名的清单。桌宠于是活像一个命令行前端，而不是一个人。
2. **派单要两次模型往返**。先调工具，再让模型根据工具结果组织一句回复。同一件事，慢一倍。
3. **内部话术漏到用户耳朵里**。提示词里白纸黑字写着「派后台任务」「task.submit」，模型照着学，用户就能看见「后台任务」四个字。
4. **问一句「某某怎么样了」要花一次工具往返**。因为状态在工具里，不在提示词里。
5. **后台任务的答复不像人话**。执行层的最终答复就是桌宠回过来说的那句话，现在它按 agent 的口径写，还会顺手提一句「我用 shell.exec 查的」。

五条都指向同一件事：**两层之间的界线画错了**。交互层应该只负责「说话」，后台任务层才负责「做事」；现在交互层自己也在做事，于是它既要背工具表，又要在两轮之间来回传话，还把内部结构漏给了用户。

---

## 2. 目标与非目标

### 目标

| | |
|---|---|
| G1 | 交互层只保留 4 个动作类工具。除「直接能答」之外的一切外部能力都经后台任务。 |
| G2 | 交互层一轮对话**只走一次模型往返**——直接回答是 1 次，派单也是 1 次。 |
| G3 | 桌宠的话里没有工具名，也没有「后台任务 / 派单 / 派发 / 工具」这类内部话术。 |
| G4 | 「某某工作怎么样了」随时能秒答：状态写在提示词里，不用调工具。 |
| G5 | 后台任务层按高质量 agent 的标准做：技能渐进披露、答复按桌宠口吻、速度与质量兼顾。 |
| G6 | 切换到「只聊天」时，先问一句；确认后停掉正在做的事。 |

### 非目标

- **不新增设置项**：交互层沿用同一个模型、同一份 LLM 配置。
- **不给后台任务加计划 / 待办工具**：宁可轻，不为了「像 Claude Code」而加。
- **不改插件协议**：不动 `plugin.json` 的字段结构。
- **不改聊天历史页与任务看板的分类结构**，不动后台任务的运行时与审批闸门。
- **不做子代理、不做任务并行编排。**

### 一条界面规则（贯穿全文）

> **工具名只进数据，不进界面。**

桌宠说的话、聊天记录页上的人话，都用工具的**人话标签**（「读文件」「列目录」「查天气」）。
唯一的例外是**任务看板**——它是给人排查「它到底调了什么」的调试面板，继续显示工具名（`fs.write`）。

## 3. 两层的分工

| | 交互层（前台） | 后台任务层 |
|---|---|---|
| 唯一的职责 | 跟用户说话 | 做事 |
| 外部能力 | **一件也没有** | 全部工具：`fs.*` / `shell.exec` / `app.launch` / `harness.run` / `skill.read` / 插件工具 |
| 自己的工具 | 4 个动作类（§4.1） | — |
| 模型往返 | **1 次** | ≤ `agent.maxSteps` |
| 看得见的状态 | 自己手头在做的事（写在提示词里，§4.4） | 自己那一件事的上下文 |
| 答复口吻 | 桌宠口吻，短 | 桌宠口吻，短（转述给用户前过一遍过滤，§4.5） |
| 审批 | 不经过闸门（四个动作都不碰用户的东西） | 走现有闸门 |

**一句话：桌宠负责说「我去办」，后台负责办完回来汇报。**

## 4. 交互层

### 4.1 工具集：只剩 4 个动作

| 工具 | 参数 | 作用 |
|---|---|---|
| `task.submit` | `title`, `brief`, `reply` | 把一件事交出去做 |
| `task.cancel` | `taskId`, `reply` | 让一件正在做的事停下 |
| `task.steer` | `taskId`, `note`, `reply` | 给一件正在做的事补一句要求 |
| `task.delete` | `taskId`, `reply` | 把一件已经结束的事收起来 |

删掉：`clock.now`、`fs.read`、`fs.list`、`capability.list`、`task.list`、`task.status`。

| 删掉的东西 | 为什么能删 |
|---|---|
| `clock.now` | 当前时间本来就在提示词里。 |
| `fs.read` / `fs.list` | 外部能力，按 G1 走后台任务。 |
| `capability.list` | 改成提示词里一行「我能：天气、待办、提醒、番茄钟、剪贴板、系统状态」。 |
| `task.list` / `task.status` | 状态写在提示词里（§4.4），按 G4 不该花一次工具往返。 |

**「我能」那一行的数据**：插件清单里每个开着（`enabled !== false`）且接给后台任务（`agentEnabled !== false`）的插件，取它的 `name`（如「天气」「待办」）。**不新增清单字段**，`description` 太长（「管理专注计时：开始、暂停、继续、重置，以及查看当前状态」），截断了没法看。

四个工具**都多一个 `reply` 参数**：要跟用户说的那一句话（一两句，口语，**别报告结果**）。它是 §4.2 那次往返能省下来的原因。`reply` 是**可选**的（模型没写就当没写）。

工具的 `description`（模型看得见的那段）要写成用户语言，不要出现「派单」「后台任务」：

- `task.submit`：「把一件事交出去做——你自己干不了、或者要花时间的事都走这里。要什么结果写在 brief 里；要跟用户说的那句话写在 reply 里。做完会另行通知你。」
- `task.cancel`：「让一件正在做的事停下。」
- `task.steer`：「给一件正在做的事补一句要求（不改它原本要做什么）。」
- `task.delete`：「把一件已经结束的事收起来（记录仍然留着）。」

`reply` 的参数说明：「要跟用户说的那一句话：一两句，口语。不要报告结果，不要提任何工具名。后面可以跟一段 `<<META>>{...}`（情绪与要记住的事），不写也行。」

### 4.2 一次模型往返

现在派单是两次：第 1 轮调 `task.submit`，第 2 轮模型根据工具结果组织一句回复。新的做法：

1. 模型在第 1 轮调工具时，**把要跟用户说的一句话一起写出来**（`reply` 参数）。
2. 工具执行成功 → **这一轮就是最终答复**，不再问模型第二遍。
3. 工具失败、或模型没写 `reply` → 不短路，循环照常走第 2 轮，让模型自己组织一句话（错误会照常喂回模型）。

实现上只改循环一处：`createAgentLoop` 新增选项 `answerFromTool`（默认 `false`，执行层不传）。

- 工具返回 `data.answer`（非空字符串）时 → 循环把它当作最终答复，`outcome = DONE`，立刻结束循环。
- 仍按老规矩把 `assistant(tool_calls)` 与 `role:'tool'` 消息补齐（接口的规矩一个字不改）。
- 一轮里调了多个工具、都给了 `reply` → 用空格连起来（最多两条）。

交互层传 `answerFromTool: true`。

**步数上限**：交互层一轮最多 `2` 步（第 1 轮调工具；第 2 轮只在工具失败或没写 `reply` 时才发生）。

**这一轮的情绪与记忆从哪来**：`reply` 里可以带 `<<META>>{...}`，交互层用现成的 `parseReply` 拆开（正文 / 情绪 / 心情 / 记忆），跟普通回答一个待遇。拿不到时：

1. 退回读**那一轮模型正文的 META**（模型在调工具时常会顺带说一句「好的，我这就去」）；
2. 都没有 → 情绪中性、不记记忆。

这样「记住 X，顺便查天气」不会因为走了派单路径就丢掉记忆。

### 4.3 提示词

交互层不再复用 `buildSystemPrompt` 拼装，改成自己组装（人设与 `<<META>>` 契约仍复用 `chat/prompt.js` 的 `metaContractLines()`，格式不许两边分叉）。

新提示词的结构（`buildInteractionPrompt`）：

```
你是「{name}」，一只住在用户桌面上的 Live2D 桌宠。
性格：{style}
关于你：{backstory}

说话规则：
- 中文口语，1~3 句，不超过 80 字（报清单、报进展可以到 300 字）。
- 不要复述用户的问题，不要 Markdown，不要表情符号。
- 只说你自己：不要提任何工具名、函数名、插件名，也不要说「后台任务」「派单」「派发」「工具」这类词——用户只看得见你这个人。
<<META 契约（沿用 metaContractLines）>>

你记得的事：
- {facts}

现在是 {年} 年 {月} 月 {日} 日 {时}:{分}。

你手头在做的事：
- {title}（{编号}，{状态}，{刚做完的那一步}，用了 {用时}）
- …
（没有事做时这一段写「现在没有别的事在忙」。）

你能做的：
- 直接答：聊天、回答你知道的事、报上面那些事的状态。
- 其它一切（查文件、跑命令、用插件、上网找东西）都交给手头去做，你只说一声「我去」。

规矩：
- 先自己答一次：能答就别交出去。
- 要交出去的时候，调用「把一件事交出去」那个工具：结果要求写进 brief，你要说的话写进 reply。
- 交出去之后，做完了它会自己回来告诉你，你不用转述结果。
- 同一个要求别交两遍：上面写着的事、还有刚才交过的，都别重复。
- 用户问「某某怎么样了」：看「你手头在做的事」那一段直接答，别去调工具。
```

对比现在的提示词，删掉的是：整段「这活儿该你自己答，还是派后台任务」的分派规则（12 行）、工具清单、插件清单、`capability.list` 的用法说明、「实时状态：后台正在跑 N 个任务」。

**提示词里不许出现工具名**（连 `task.submit` 都不许）——工具名在工具表里，模型自己会看；提示词里再写一遍既费 token 又容易诱导模型把名字说给用户听。

### 4.4 「你手头在做的事」

这是 G4 的落点：状态直接写进提示词，模型不需要调工具就能回答「某某工作怎么样了」。

**数据来源**：`agentTasks.list()` 那个精简视图（`taskId` / `title` / `status` / `lastStep` / `result` / `elapsedMs`）。

**要带任务号**：`task.cancel` / `task.steer` / `task.delete` 都要 `taskId`。已经结束的事不在状态块里（那里只有未结束的），所以**派单记录里也必须留着号**（§4.7）。

**一步的名字要是人话**：状态块里不能出现 `fs.list`（进了提示词，模型就会照着说给用户听）。所以状态块用工具的**人话标签**：

- `agent/tasks.js` 的 `brief()` 增一个字段 `lastStepLabel`（工具的 `label`，如「列目录」）；`lastStep` **保持工具名不变**（任务看板还要用，§2 的例外）。
- `loop.js` 的 step 事件补上 `label: tool.label`（现在只有外部 harness 的事件带 label）。这一个改动同时让**聊天记录页**的步骤记录显示人话（`stepRecord` 的正文取 `label || 工具名`）。
- `skill.read` 的 label 从「读技能说明」改成 **`读文档`**——「技能」是内部词，桌宠嘴里不该有。

**排版**：

```
你手头在做的事：
- 找 F 盘里的视频（t-1，进行中，刚读完一个目录，用了 12 秒）
- 查北京天气（t-2，排队中）
```

- 状态用中文短句（`进行中` / `排队中` / `等你点头`），沿用 `TASK_STATUS_TEXT`。
- 没有在做的事时这一段写「现在没有别的事在忙」——**不要留空**，留空模型会自己编。
- 最多列 5 条，超出的按「还有 3 件在排队」概括。
- 标题是桌宠自己在派单时写的那句（`title`），天然是用户语言。

### 4.5 话术过滤

三道防线，缺一不可。

**第一道：提示词**（§4.3）。模型被明确禁止说这些词。绝大部分情况到这儿就结束了。

**第二道：过滤层**（新增 `src/main/assistant/layer/speech.js`）。

它作用在**所有对用户可见的桌宠文字**上，落点有三个：

| 落点 | 覆盖什么 |
|---|---|
| 交互层内部 | 流式正文（逐字吐出去的那部分）与最终答复 |
| `index.js` 的 `runChat` | 兜底路径（模型不支持工具调用时退回的普通对话） |
| `index.js` 的 `notify` | 后台任务做完后的汇报 |

**写进聊天记录的文字也过滤**：模型下一轮会读到自己上一轮说过的话，不滤它就会自我强化那些黑话。

规则：

| 类别 | 例子 | 处理 |
|---|---|---|
| 工具名 | `weather.get`、`fs.read`、`task.submit` | 换成「这件事」。工具名从工具表取（交互层那 4 个 + 插件与内置工具），**按已知名字精确匹配**，不按 `a.b` 这种形状乱猜——文件路径 `a.mp4` 不能被误伤。 |
| 内部话术 | 后台任务、派单、派发、派出任务 | 后台任务 → 这件事；派单 / 派发 → 安排；派出任务 → 这件事。 |
| 内部名词 | 任务、工具、插件、MCP、<<META>> | 任务 → 事情；工具 / 插件 / MCP / `<<META>>` → 删掉。 |

删完之后做一遍**收拾**：去掉空括号、合并多余空格、去掉首尾多余的逗号句号。

**删空了就用兜底句**：「这个我记下了。」

**流式的那一层**：模型是 SSE 逐字吐的，一个禁词可能被切成两半（「后台任」+「务」）。所以过滤器要**按住尾巴**——跟 `chat/prompt.js` 里 `createStreamSplitter` 处理 `<<META>>` 是同一个套路：缓冲区的尾巴如果可能是某个禁词的前缀，就先按住，等看清了再吐。常态下尾巴是 0 个字，不影响逐字显示。

**第三道：兜底**。过滤之后如果还剩下禁词（表里有、但没被上面规则覆盖的），整句换成兜底句。宁可换掉一句，也不要把内部黑话漏给用户。

### 4.6 速度账

| | 现在 | 改后 |
|---|---|---|
| 直接回答的模型往返 | 1 | 1 |
| 派单的模型往返 | 2 | **1** |
| 每轮带的工具定义 | 10 个 | 4 个 |
| 系统提示词 | ~900 字 | ~350 字 |
| 查一次任务状态 | 1 次工具往返 | 0（写在提示词里） |

**`maxTokens`：要用下限，不是上限。**

`max_tokens` 只是**生成上限**，不影响延迟（模型吐到 EOS 就停）。但工具参数与正文**共用**这一个额度：`title` + `brief`（≤ 200 字）+ `reply`（含 META）一起塞进 JSON，上限太小就会被截断成非法 JSON → 工具调用失败 → 退回第 2 轮 → G2 直接破功。

所以交互层用 `max(用户设置, 1024)`，跟执行层已有的 `AGENT_MIN_MAX_TOKENS = 2048` 是同一个套路（`createModelCaller` 的 `minMaxTokens` 参数现成）。用户设置得更高就按用户的来。

### 4.7 派单记录：宠物的说法 + 号

`dispatchRecord` 的可见文字现在是「`task.submit` 派了个任务：xxx（任务 t-1）」——三个毛病：工具名、「派了个任务」、以及「任务」二字。

改成：

```
开始做：找 F 盘里的视频 t-1
```

- 工具名只留在 `meta.tool`（审计用）。
- 任务号留着（`task.cancel` / `task.steer` / `task.delete` 要它，见 §4.4）。
- 聊天记录页的 `dispatchLabel()`（`plugins/chat-history/pages/format.js`）按 `meta.tool` 分派，要一并改成宠物的说法：

| 工具 | 新文案 |
|---|---|
| `task.submit` | `开始做：{title}` |
| `task.cancel` | `停掉了：{title}` |
| `task.delete` | `收起来了：{title}` |
| `task.steer` | `给那件事补了一句要求` |

## 5. 后台任务层

后台任务层是「高质量 agent」，但这一轮**不加新工具**——加一个计划工具要多一轮模型往返，与「兼顾速度和质量」的取舍不符。做四件事。

### 5.1 最终答复按桌宠口吻

执行层的最终答复**就是桌宠回过来说的那句话**（`notify` → `say`）。所以它的口径要改：

```
回答规则：
- 这是桌宠回给用户的一句话：中文口语，1~3 句，不超过 80 字。
- 只说结果和要点（「找到了，F 盘里有 3 个视频」），不要复述过程。
- 不要提任何工具名、函数名、插件名，也不要说「后台任务」「派单」「派发」这类词。
- 拿不准就照实说，别编。
```

详细结果留在任务看板与步骤记录里，气泡里只留这一句。

**顺带修一个现存缺口**：执行层答复里的 `<<META>>`（情绪 / 心情 / 要记住的事）现在被 `parseReply` 拆出来之后就**扔掉了**——`agent/tasks.js` 只把 `result.text` 交给 `notify`。改成把 `emotion` / `mood` / `memories` 一并交给通知路径：情绪驱动桌宠的表情，记忆并进长期记忆。

### 5.2 技能：说明改成「什么时候用」

渐进披露的三级结构**已经有了**（提示词里只有名字 + 说明 → `skill.read` 读正文 → 再读正文引用的文件），不动结构，改两处：

1. **技能说明写成「什么时候该用它」**，而不是「它是什么」。模型据此判断要不要读，判错的概率低得多。
   - 现在：`weather` 的说明是「查当前天气，以及设置默认城市」。
   - 改成：`weather` 的说明是「用户问天气、气温、要不要下雨、下不下雪的时候用它」。
2. **「先读说明书再动手」从建议变成硬规矩**：模型要用某个插件的工具之前，先 `skill.read` 读它的正文。现在提示词里已经写了这一句，但要写得更硬——「**不许**在没读说明书的情况下调这个插件的工具」。
3. 插件开发者指南（`docs/开发说明/插件开发指南.md`）的 `skill` 段要补上这条约定，并给现有插件的 `skill.md` 补一句「什么时候用」。

正文里提到的被关掉的工具要补一句「已被用户关闭，不要调用」——现有的 `appendDisabledNote` 已经做了，保留。

### 5.3 派单契约：后台任务一次做对

后台任务的质量，八成取决于派单时那份 `brief` 写得好不好。派单要带四样东西（现在的 `task.submit` 已经带了前两样）：

1. **用户原话**（逐字）——简报写歪了还能靠原话找回来；
2. **`title`**——一句话说明在做什么；
3. **`brief`**——要什么结果、**什么算完成**、有什么约束（≤ 200 字）；
4. **相关历史**——最近几条 `user` / `reply`。

提示词里对 `brief` 的要求要写清楚「**什么算完成**」这一条。现在只说「要什么结果」，后台任务常常不知道边界在哪，于是自己加戏。

### 5.4 速度与质量的平衡

后台任务不是越快越好——它要的是**一次做对**。所以：

- **工具结果截断**（`MAX_AGENT_TOOL_RESULT_CHARS = 1500`）保持不变：截短了模型会以为文件就这么长，反而做错判断。
- **上下文压缩**（8 轮 / 24000 字）保持不变。
- **派单时把话说清楚**（§5.3）是最大的提速手段：少一轮 steer 往返，比省一步工具值钱。
- **不加计划工具**：多一轮模型往返换一点结构化收益，不划算。

## 6. 「只聊天」模式：先问一句，再停掉手上的事

设置里的派单模式有两个档：`auto`（能派活）与 `off`（只聊天）。

**关掉派单时，交互层一个工具都不给**（现在的行为）：桌宠只能聊天，不查本机、不翻文件、不跑命令，也不派单。

新增：**切到「只聊天」时，先弹确认框；确认后停掉正在做的事。**

| | |
|---|---|
| 确认框 | 复用已有的原生确认框模式（`src/main/index.js` 的 `deleteModel` 就是这么做的）：`dialog.showMessageBox`，父窗口是设置窗口。文案：「切到「只聊天」后，桌宠不再接新活，正在做的事也会停下来。确定吗？」 |
| 问的时机 | **保存之前**。用户点「取消」→ 下拉框退回原来的值，什么都不改。 |
| 停任务的位置 | **主进程**：`createAssistant.update(patch)` 里发现 `agent.dispatch` 从非 `off` 变成 `off` → 把所有未结束的任务停掉。这是唯一的收口——不管这个改动从哪条路来（设置页、插件、代码），都会停。 |
| 停完说什么 | 不弹气泡（用户在设置窗口里，看板上能看到任务变成「已取消」就够了）。 |
| 设置页文案 | `DISPATCH_MODE_INFO.off.hint` 现在写着「桌宠只跟你聊天：读时间、读单个文件，其他事一概不派。」——`clock.now` 与 `fs.read` 这一版都没了，这句话会骗人。要改成：「桌宠只跟你聊天：不查本机、不翻文件、不跑命令，什么都不替你做。」 |

## 9. 风险与取舍

| 风险 | 怎么办 |
|---|---|
| 模型不写 `reply` | 不短路，走第 2 轮由模型自己说——只是慢一点，行为与今天一样。 |
| 模型把工具名说给用户听 | 三道防线（提示词 → 过滤 → 兜底）。过滤层按已知工具名精确匹配，不误伤文件路径。 |
| 状态写在提示词里，模型对着旧状态瞎说 | 提示词每轮重建，状态是当轮最新的。唯一的不一致是「这一轮进行中任务刚结束」——完成通知会以桌宠的话单独送达，用户看到的是两句话，不冲突。 |
| 删掉 `task.list` / `task.status` 后，用户问「我一共派过几件」答不上来 | 派单记录仍在交互层的上下文里（`dispatch` 分类），模型能数出派过几件、在做的事看状态块。 |
| 4 个工具都带 `reply`，模型可能把「结果」写进 `reply` | 提示词明确要求「别报告结果」；结果由后台任务完成后单独送达。写错了也只是顺序颠倒，不会丢信息。 |
| `reply` 里带 `<<META>>`，模型写歪了 | `parseReply` 拆不出就当没有（情绪中性）；过滤器还会把漏出来的 `<<META>>` 标记删掉。 |
| 交互层提示词里不再有工具清单，模型会不会不知道自己能干什么 | 工具表本身就带 `description`；再加上「你能做的」两行与「我能：……」一行。 |
| 执行层的答复变短，细节丢了 | 细节在任务看板与步骤记录里（`board()`），本来就给人看。 |
| 看板改成不显示人话标签后，外部助手的步骤看不出细节了 | 人话标签改成悬停提示（`title`），工具名仍然显眼。 |
| 切「只聊天」会停掉正在做的事 | 先弹确认框；用户不点确定就什么都不改。 |
