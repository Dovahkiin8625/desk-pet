# 插件的独立窗口：宽版与窄版

> 日期：2026-11-12
> 状态：待评审
> 范围：`src/shared/plugin.js`、`src/main/plugins/host.js`、`src/main/plugins/window.js`、`src/renderer/panel/index.html`、`src/renderer/plugin-window/index.html`、`src/renderer/ui/{theme.css,blocks.css}`、`plugins/*/plugin.json`、`plugins/{music-player,chat-history,clipboard,tasks,screen-recorder}/pages/*`
> 相关：`docs/开发说明/插件系统架构.md`、`docs/开发说明/插件开发指南.md`

---

## 1. 为什么要改

面板里打开插件与在新窗口打开插件，**界面上几乎分不出来**：

- 面板宽 420，独立窗口默认 360×420（`src/shared/plugin.js` 的 `PLUGIN_WINDOW_LIMITS`）；
- 积木界面两处**共用同一份** `blocks.js` + `blocks.css`，排版一模一样；
- 插件自带页面两处**也是同一份文件**（`iframe` 里加载），而那份文件里只有一个
  `body.dp-panel` 的 JS 开关——它管的是**高度策略**（面板按内容撑开、窗口铺满视口），跟宽窄无关。

于是「在哪儿打开」这件事用户在界面上读不出来，两边又都塞不下多少东西。

要的是**同一个插件的两种形态**：面板是「手机版」——窄、单列、够用就够；
独立窗口是「PC 版」——宽、信息全、一屏看完。

---

## 2. 目标与非目标

### 目标

| | |
|---|---|
| G1 | 独立窗口默认更大（720×560），内置插件的窗口尺寸也调成 PC 尺寸 |
| G2 | 面板与窗口**看起来就是两种东西**，而宽窄由**可用宽度**决定（不靠 if/else 分叉） |
| G3 | 宿主画的积木界面在宽窗口里「一屏看完更多」——条目型内容分两列 |
| G4 | 插件自带页面在宽窗口里有一版宽布局（5 个内置插件都做） |
| G5 | 用户拖过的窗口尺寸被记住（按插件 id），且有一条「恢复默认尺寸」的路 |
| G6 | 面板这一侧**外观不变** |

### 非目标

- **不给插件协议加字段**：`window.width/height` 字段名与语义不变，它一直就是「独立窗口的尺寸」。
- **不新增块类型**：宽版排版是 CSS 的事，不是协议的事。
- 不动小部件的尺寸与布局（小部件按清单的尺寸，是另一种东西）。
- 不改面板的尺寸与交互。

---

## 3. 一条规则

> **宽窄由宽度决定，不由「在哪儿打开」决定。**

面板永远是窄的（它就 420 宽），独立窗口默认是宽的（720 起步）。
但**判据是「现在有多宽」**，不是「我是哪个窗口」——所以用户把窗口拖窄了，
界面会自己回到窄版，而不是硬撑着两列。

这条规则落到代码上就是**一个断点**：`560px`（可用宽度）。

---

## 4. 两个机制（为什么不是一个）

宿主画的积木界面与插件自带页面**不在同一个文档里**，容器查询跨不过 iframe 边界，
所以两处各用各的、但**断点是同一个数**。

### 4.1 宿主画的积木界面（容器查询）

面板与独立窗口壳里的积木界面是**同一份文档**里的两块内容，
宿主给内容区套上 `.surface`（`src/renderer/ui/theme.css` 里已经定义好的那个类，
只是从来没人用过），`blocks.css` 用 `@container surface (min-width: 560px)` 切宽版。

**容器套在哪一层很要紧**：要套在**宽度等于 iframe 宽度**的那一层上——
面板的 `<section id="plugin">`、独立窗口壳的 `#win`。
这样容器量到的就是「这个界面有多宽」，与插件页的视口宽度**是同一个数**，
两个机制才不会在同一个窗口里混搭（积木已经是宽版、插件页还是窄版）。

| 落点 | 容器（= iframe 宽度） | 积木自己的内容宽度 | 落到哪一版 |
|---|---|---|---|
| 面板 `<section id="plugin">` | ≈ 394 | ≈ 366 | 窄版 |
| 独立窗口壳 `#win` | 窗口宽 − 2 | 窗口宽 − 30 | 宽版（720 的窗口） |

### 4.2 插件自带页面（媒体查询）

插件的页面在 iframe 里，是**另一个文档**：容器查询查不到 iframe 外面去。
所以插件页按**自己的视口宽度**（就是 iframe 的宽度）用 `@media (min-width: 560px)` 切版。

| 落点 | 页面视口宽度 | 落到哪一版 |
|---|---|---|
| 面板里的 iframe | ≈ 394 | 窄版 |
| 独立窗口里的 iframe | 窗口宽 − 2 | 宽版（720 的窗口） |
| 小部件（页面原样加载） | 清单写的宽度（都 < 560） | 窄版 |

> `theme.css` 里 `.surface` 那段注释说「插件页面用 `@container surface (…)`」——
> 那是**跨不过 iframe 边界**的，写法有误。这次一并改对：
> 积木界面用容器查询，插件页面用媒体查询。

## 5. 尺寸

### 5.1 默认尺寸

`PLUGIN_WINDOW_LIMITS`（`src/shared/plugin.js`）里的**默认值**改大；
上下限不动（200×120 ～ 1200×900）。

| | 旧 | 新 |
|---|---|---|
| 宽 | 360 | **720** |
| 高 | 420 | **560** |

影响的是**没写 `window` 段**的插件（宿主合成的那份默认规格）。

### 5.2 内置插件的窗口尺寸

清单里的 `window.width/height` 就是独立窗口的尺寸，这轮按「PC 感」调大：

| 插件 | 旧 | 新 |
|---|---|---|
| todos 待办 | 320×380 | 640×600 |
| reminders 提醒 | 320×380 | 640×600 |
| weather 天气 | 320×320 | 620×520 |
| system 系统状态 | 320×300 | 640×480 |
| pomodoro 番茄钟 | 300×300 | 620×520 |
| clipboard 剪贴板 | 380×460 | 720×560 |
| chat-history 聊天记录 | 520×640 | 860×680 |
| music-player 音乐播放器 | 380×520 | 780×620 |
| tasks 后台任务 | 420×560 | 760×620 |
| screen-recorder 录屏 | 900×620 | 900×620（不动，它本来就是宽的） |

每一个都 ≥ 620 宽：减去壳的边框与内边距，内容区仍 ≥ 560 → 宽版成立。

### 5.3 记住用户拖过的尺寸

清单里的尺寸是**第一次打开**时的尺寸；用户拖过之后就该记住。

- 存哪：`plugins.json`（宿主已经在管这个文件：启用状态、agent 开关、插件配置）
  新增一段 `windowSizes: { "<pluginId>": { "width": n, "height": n } }`。
- 宿主（`host.js`）暴露两个口子：`getWindowSize(id)` / `setWindowSize(id, {width, height})`；
  写入时按 `PLUGIN_WINDOW_LIMITS` 的上下限夹一下。
- 窗口控制器（`window.js`）：建窗时**记住的有就用记住的**；
  用户拖动窗口后（`resize` 事件，去抖 400ms）把新尺寸写回去。
- **只记窗口形态**，小部件的尺寸是清单定的，不记。

### 5.4 怎么回得到默认尺寸

记住的尺寸会**盖住**清单里的尺寸：用户拖过一次之后，清单里写多少都不生效了
（插件作者后来改了窗口尺寸，用户也看不到）。所以要给一条回去的路：

**独立窗口的标题栏上多一个「⤢」按钮**（挨着置顶 / 变小 / 关闭），
点一下就把窗口恢复成清单里写的尺寸，同时把记住的值也改成它（等于清掉记忆）。

窗口不能最大化（`maximizable: false`），所以这个按钮不与「最大化」抢同一个手势。

## 6. 宽版长什么样

### 6.1 宿主画的积木界面（`src/renderer/ui/blocks.css`）

只有「条目型」的块分两列——分两列对它们有意义，其余块保持单列：

| 块 | 宽版 |
|---|---|
| `list` | 分两列（`columns: 2`），一屏能看完更多条目 |
| `settings` | 分两列（label + 控件一行，两行一组） |
| `messages` | 单列（对话是线性的），只是更宽 |
| `text` / `input` / `buttons` / `toggle` | 单列，留白更松 |

> 自带页面的插件走自己的页面，宿主**不再**给它们加 `settings` 块——
> 所以积木里的 `settings` 目前只有**番茄钟**看得到（三个声明了 `settings` 的插件里，
> 剪贴板与音乐播放器都自带页面）。

### 6.2 插件自带页面（5 个内置插件各一版宽布局）

一律用 `@media (min-width: 560px)`，加在各自页面的样式里：

| 插件 | 宽版 |
|---|---|
| music-player | 两栏：左＝正在播放 + 进度 + 控制；右＝播放列表 / 音乐库（不再被 `max-height` 掐住） |
| chat-history | 一天一组，组内的对话块分两列，组标题跨列 |
| clipboard | 列表分两列（卡片式） |
| tasks | 总览层两列：左＝当前任务，右＝待你点头 + 任务列表 |
| screen-recorder | 本来就是两栏；它的 `.studio` **自己就是那个 `surface` 容器**，所以继续用容器查询，只把窄版阈值从 460 对齐到 560（面板里与窗口里的样子都不变） |

## 9. 取舍与风险

| 决定 | 代价 | 为什么 |
|---|---|---|
| 宽窄由宽度决定，不加「我是宽版吗」的标志位 | 插件要写两套样式 | 一套 CSS 断点胜过一套运行时状态；窗口拖窄了界面自己会变 |
| 积木用容器查询、插件页用媒体查询（两个机制） | 插件作者要记两件事 | 容器查询跨不过 iframe 边界，只能这样；断点是一个数，记忆成本不高 |
| 只给条目型块分两列 | 番茄钟这类块在宽窗口里只是更空 | 分两列对「一条条的东西」有意义，对「一段话」没意义 |
| 记住用户拖过的尺寸 | 清单里的尺寸只管第一次 | 用户拖过就说明他有偏好；记在 `plugins.json`，与插件配置同源 |
| 窗口变大会在屏幕上「放不下」 | 小屏上窗口会被夹进工作区（`placeBesidePet` 的既有行为） | 录屏早就是这个体量；为了小屏把窗口做小，等于回到今天的问题 |

**已知的一个副作用**：用户把窗口拖到 560 以下，宽版会退回窄版——
这是 §3 那条规则要的效果，不是 bug。
