# Live2D 桌面宠物 第五部分 — AI 对话能力 — 设计规格

> 本文档是 `2026-11-01-live2d-desk-pet-plugin-panel-design.md`（下称「面板规格」）的续篇。
> 面板规格定了「点桌宠 → 搜索 → 打开插件界面」的入口形态；
> 本文解决的是**对话本身**：桌宠怎么回话、怎么记住、怎么有情绪。
>
> 覆盖 `idea.md` 第四部分「AI 对话能力」中的五项：
> LLM 对话、角色人设、上下文记忆、情绪联动、主动搭话。
> **不含** ASR（语音输入）——它要一整套录音与流式转写，属于另一件事。
>
> 裁决记录见 `docs/decisions.md` 第五部分（#61~#72）。

## 1. 目标与范围

### 1.1 要补的

| 现状 | 目标 |
| --- | --- |
| 桌宠只能说写死的句子 | **能聊天**：按自己的性格回答用户说的话 |
| 没有「谁」的概念 | **人设**：名字、性格、背景，设置里可改 |
| 没有记忆 | **短期**（最近几轮）+ **长期**（模型抽取的事实），可查看可清空 |
| 情绪只由用户的动作决定 | **对话也影响情绪**：回复带情绪，直接驱动表情 |
| 桌宠永远被动 | **主动搭话**：按时间/事件主动开口 |

### 1.2 范围外

- **ASR / 语音唤醒**：需要麦克风权限、流式转写与一套新的录音界面。
- **多模态**（看图说话、语音输入）。
- **插件市场的分发机制**：本文的插件是内置的。

## 2. 总体架构

```
面板输入框 ──panel:chat──▶ assistant.chat(text)
                                │
                                ├─▶ 后端注册表 ──▶ plain 后端 ──▶ llm/openai.js ──▶ OpenAI 兼容端点
                                │   （将来：agent 后端）      │  onDelta(增量)
                                ▼                            ▼
                        state.chat.messages ◀── parseReply() ─┘
                                │
                                ├─▶ bubble.openStream / append / end   → 桌宠旁边的气泡（流式）
                                ├─▶ onEmotion(emotion, mood)           → 桌宠换表情
                                └─▶ speakNow(text)                     → MiniMax TTS 念出来
```

**主进程仍是唯一的状态来源**：对话历史、人设、LLM 配置都在 `assistant.json` 里。

## 3. 交互形态

### 3.1 输入：复用面板的输入框

**不另做聊天界面**。点桌宠弹出的那个输入框就是聊天输入框：

- 输入的话**匹配不到任何插件** → 回车＝发给桌宠；
- 匹配到插件 → 回车＝打开那个插件；
- **Ctrl+Enter 永远发给桌宠**（哪怕这句话也匹配得到插件）；
- 结果列表末尾**常驻**一条「和桌宠聊天」，可以选中它。

聊天走的是**独立的 `panel:chat` 通道**，不走插件动作通道——
后者带「请求序号」（后来的请求作废先前的），会把聊天误丢掉。

### 3.2 回复：桌宠旁边的气泡，流式

回复**不在面板里显示**，而是在桌宠旁边的**气泡**里逐字冒出来：

- 面板在发出消息后**收起来**：气泡与面板用同一套摆位算法，
  气泡会正好落在面板上把它盖住（气泡不透明）；
- 气泡进入**流式**形态：开口 → 逐字追加 → 定稿 → 15 秒后自动消失；
- 流式期间**锁定气泡的方向**：气泡长大后可能从「头顶」变成「脚下」，
  换边会让小尾巴跳一下；
- 尺寸上报**节流**：每个字都报一次的话，窗口会被缩放几百次。

### 3.3 历史：单独的插件

聊天发生在气泡里，面板里只看得到输入框，所以历史要**单独做一个插件**（`聊天记录`）。
设置页里还能看到「它记住的事」并一键清空——用户有权知道桌宠记住了什么。

## 4. 大模型客户端

`src/main/assistant/llm/openai.js`，骨架照抄 `assistant/tts/minimax.js`：
注入 `fetchImpl`、纯函数 `buildRequestBody`、错误类、域名探测。

### 4.1 接口

```
POST {baseUrl}/chat/completions
Authorization: Bearer <API_KEY>
{ model, messages, temperature, max_tokens, stream }
```

`baseUrl` 指向 `/v1`（OpenAI 兼容的惯例），客户端自己拼 `/chat/completions`；
填了完整地址就原样用。

### 4.2 五个坑

1. **地址要自己拼**：`base_url` 指向 `/v1`，客户端补 `/chat/completions`。
2. **流式是 SSE**：`data: {json}\n\n` 一帧一帧，`data: [DONE]` 结束；
   有的帧只带 `role` 不带 `content`，必须判空。
3. **中文会跨块**：一个汉字 3 字节，网络分块边界可能切在中间。
   必须用带状态的 `TextDecoder`（`{stream:true}`），
   每个 chunk 单独 `toString()` 会得到 `��`。
4. **错误分类**：401/403 鉴权、429 限流、400/404/422 请求本身不对、5xx 服务端。
   鉴权失败**要**换域名重试——MiniMax 的 key 是分区域的。
5. **`max_tokens` 与 `max_completion_tokens` 不能同时发**，
   `stream_options` 同理（严格的服务端会报「未知字段」直接 400）。

### 4.3 探测规则

| 错误 | 换地址？ | 为什么 |
| --- | --- | --- |
| 鉴权 / 网络 / 限流 / 服务端 | **换** | 这个地址现在不伺候我们 |
| 请求本身不对 / 格式错误 | 不换 | 换也是同样的结果 |
| **流已开始后失败** | 不重来 | 用户已经看到半句了，重来会重复 |

## 5. 一次调用同时拿三样

回复正文、这一轮的情绪、值得记住的事——一次模型调用全拿回来。

### 5.1 正文在前、元数据在后

```
<回复正文，最多 3 句，中文口语>

<<META>>{"emotion":"happy","mood":5,"memories":["用户喜欢喝美式"]}
```

**不能让模型只回一个 JSON 对象**：那样气泡在整段 JSON 生成完之前都是空的，
流式就没了。

### 5.2 解析要能容错

四种形态都要认：正文 + `<<META>>` + JSON；整个回复是 JSON 对象；
```json 围栏包着的 JSON；其它（整段当正文，情绪 `neutral`）。

**元数据坏了绝不能丢掉正文**——丢情绪比丢回复好得多。

情绪标签必须是 `neutral/happy/shy/surprised/sad/angry/tired` 之一
（与 `src/renderer/pet/emotion.js` 的 `EMOTION_EXPRESSION` 的键一致，
decisions.md #49 记的就是「标签写错会静默失效」），非法值退回 `neutral`。
`mood` 夹在 -10..10；`memories` 最多 2 条、每条 200 字。

### 5.3 流式：正文与元数据要分开显示

标记符可能跨 chunk 边界，所以**按住可能成为标记符的那截尾巴**——
只有真正可能是 `<<META>>` 前缀的几个字被按住，其余照常显示。
这段逻辑放在**后端**里，气泡只管「收到什么显示什么」。

## 6. 后端接缝

一个后端就是一个对象：

```js
{
  id: 'chat',
  label: '普通对话',
  chat(ctx) → Promise<ChatResult>
}
```

```
ctx = { system, messages, trigger, config, signal, onDelta, onEvent }
ChatResult = { text, emotion, mood, memories, baseUrl? }
```

**注册表放在助理里**（`createBackendRegistry()`），`state.llm.backend` 选当前后端。

将来做 agent（nanobot / openclaw 那种会调工具、会多步思考的形态）时，
实现同一个接口再注册一行就行——**气泡、历史、情绪联动、插件面板都不用改**。

- `ctx` 是**对象**而不是位置参数，就是为了以后往里加 `ctx.tools` / `ctx.runTool()`
  而不动所有后端的调用方式；
- `ctx.onEvent` 先留着不用——那是给 agent 的中间事件（工具调用、步骤）用的；
- 「普通对话」就是「零个工具、一步」的 agent，上层分不出两者的区别。

## 7. 状态

```jsonc
{
  "llm": {
    "enabled": false,                 // 默认关：要花钱、要联网
    "baseUrl": "https://api.minimaxi.com/v1",
    "model": "MiniMax-Text-01",
    "temperature": 0.7,
    "maxTokens": 800,
    "maxTokensField": "max_tokens",
    "backend": "chat",
    "lastWorkingBaseUrl": "",
    "persona": { "name": "小桌", "style": "活泼、亲切，偶尔犯困", "backstory": "" },
    "proactive": { "enabled": false, "minIntervalMs": 1800000, "lastAt": 0, "nextAttemptAt": 0, "consecutiveFailures": 0 }
  },
  "chat": {
    "messages": [{ "role": "user", "text": "…", "at": 0, "proactive": false }],
    "facts": ["用户喜欢喝美式"]
  }
}
```

**截断放在 `sanitizeAssistant`**（读写共同的唯一关口）：
历史 40 条、事实 50 条、单条 2000 字、单条事实 200 字。
提示词里只带最近 12 条——「记多少」与「发多少」是两回事。

## 8. 主动搭话

在助理的 `tick()` 里**最后**检查（优先级最低，绝不能挤掉提醒和报时）。

条件全满足才搭话：对话开着、主动搭话开着、桌宠可见、没有正在进行的对话、
距上次搭话超过间隔、用户 5 分钟没说话、启动 10 分钟内不搭话、
不在深夜（23:00–08:00）、上次失败已过退避时间。

失败**不重试轰炸**：指数退避（间隔 × 2^失败次数，封顶 6 小时），
只写终端日志，**不弹错误气泡**（一次失败的搭话不该在桌面上留个错误提示）。
主动说的话会写进历史并标记 `proactive: true`。

## 9. 凭证

对话的 key **单独存**（`credentials.json` 的 `llmApiKey` 字段），
但**留空就沿用 MiniMax 的 key**——大多数人只有一个 key。

设置页里能看到「已配置 ****abcd」还是「沿用 MiniMax Key」，
**永远不回显明文**。

## 10. 测试策略

| 层 | 覆盖 |
| --- | --- |
| 单元 | 客户端：SSE 解析、**中文跨块不乱码**、错误分类、探测规则；回复解析的四种形态与容错；提示词与上下文裁剪；状态的规整与截断 |
| 端到端 | 本地 **SSE 桩服务**：回复逐字出现在气泡里、元数据不外泄、消息与记忆落盘、情绪联动、Ctrl+Enter、没有 key/接口报错时不崩、聊天记录插件 |

真实接口只人工验一次（同 TTS 的规矩）。

## 11. 验收标准

1. 点桌宠 → 输入「在吗」→ 回车 → 面板收起，桌宠旁边的气泡**逐字**出现回复。
2. 气泡里**看不到** `<<META>>` 之类的元数据。
3. 输入「todo」→ 回车 → 打开待办插件；**Ctrl+Enter** → 发给桌宠。
4. 回复里的情绪会反映到桌宠表情上。
5. 「聊天记录」插件能看到聊过的内容，并能一键清空。
6. 设置页能改接口地址、模型、人设、主动搭话；能看到并清空「它记住的事」。
7. 没有 key、接口 401、接口超时——**不崩**，且用户看得懂出了什么事。
8. `npm test` 全通过。
