# 聊天记录页面 · 按「一次发话」分层重设计

> 设计规格。改这块代码前先读这份，读不懂的地方先问，别猜。

## 1. 背景与动机

现在的聊天记录插件（`plugins/chat-history/`）把记录按时间顺序铺成一条流：对话气泡、派单提示、任务卡，一样重。用户说"我发了一次消息"时，看不到**那一句话引发了什么**：

- 桌宠跟模型之间来回了几次、模型中途说了什么、调用了哪些工具——**一个字都没记**；
- 交互层派给后台的那份任务说明（brief）——**只留了标题，正文丢了**；
- 后台任务做完，桌宠说的话**只弹了个气泡就散了**，不落记录；
- 后台任务异步完成，完成记录和当初那句话在时间上隔得很远，页面上只能靠"时间挨着"硬凑。

用户要的是：**看清自己发的一次消息之后，桌宠跟大模型之间、交互层与后台之间发生了什么。**

## 2. 目标与非目标

### 目标

1. 页面以「一次发话」为块，块内分**桌宠这边**（交互层跟模型的往来）与**后台那边**（执行层干的活）两段。
2. 三级折叠：块 → 段 → 明细。默认只展开该展开的。
3. 补齐数据：模型每轮说了什么、交互层的工具调用、派单的交底原文、后台完成时桌宠说的话。
4. 后台任务异步完成后，**回到它被派出去的那一块**里，不另起炉灶。

### 非目标（这轮不做）

- **搜索 / 筛选**：记录分块折叠之后查阅已经够用，真需要再加。
- **记模型的原始请求体**（完整 system prompt、全部历史消息）：一页下来全是重复的历史，页面会变成日志文件。
- **执行层内部的每一轮模型正文**：执行层的工具调用已经记了（`step`），再记正文是重复。
- **折叠状态的持久化**：展开状态只在本次会话内记住，重新打开页面回到默认。
- **按 layer 再过滤模型上下文**：规格 §7.3 定的是"执行层完成 → `reply`"，而 `CHAT_KIND_FOR_LAYER` 里 `reply` 两层都看得见——本轮不动。执行层看见别的任务的结果是既有行为，不是这次引入的。

### 反目标（做出来算失败）

- 界面上出现 `kind`、`taskId`、`layer`、`dispatch` 这类字段名或代码逻辑说明。
- 页面把"一次发话"拆散到时间线的各个角落。
- 为分层去改记录的持久化格式（`assistant.json` 的形状不动）。

## 3. 现状盘点（设计前的事实）

| 事实 | 出处 |
|---|---|
| 记录有六种分类：user / reply / task / step / approval / dispatch | `src/shared/assistant.js` 的 `CHAT_KIND` |
| 只有 user 与 reply 进模型上下文；dispatch 只进交互层 | 同上，`CHAT_KIND_FOR_LAYER` |
| 新分类**必须**加进 `CHAT_KIND`：不认识的 kind 会被 `chatKindOf` **降级成 `reply`**——不是被丢掉，而是混进两层模型上下文（比丢掉更糟） | `src/main/assistant/chat/memory.js` 的 `normalizeChatEntry`；`src/main/assistant/state.js` 的 `sanitizeAssistant` |
| `meta` 单串 ≤1000 字、单条 ≤4000 字、数组 ≤20 项、深度 ≤4 | `src/main/assistant/chat/memory.js` 的 `capMeta` |
| 派单记录原来只有 tool / taskId / title / action，**没有 brief**（本轮补上了 brief） | `src/main/assistant/agent/record.js` 的 `dispatchRecord` |
| 执行层的工具调用记成 `step`（带 taskId / args / result / error） | 同上，`stepRecord` |
| 交互层**没有注册进后端表**——`backends.register` 只有 `chat` 与 `agent` | `src/main/assistant/index.js` |
| 后台任务完成的答复只弹气泡，不落记录 | `src/main/assistant/agent/tasks.js` 的 `notify` → `say` |
| 双层 agent 的 **Task 4（两层接线）没做**，前三个 Task 的代码已就位 | `docs/superpowers/plans/2026-11-08-two-layer-agent.md` |
| 页面现在是一条平铺的时间流，唯一分级是任务卡里的 `details` | `plugins/chat-history/pages/` |

## 4. 设计

### 4.1 页面结构

```
今天
│
├─ ▾ 14:32  「F 盘 video 下有什么」            后台运行中
│    │
│    ├─ 桌宠这边
│    │    问模型 MiniMax-M2 · 3 轮          ▸ 展开：每轮模型说了什么
│    │    调了一次剪贴板                     ▸ 展开：参数与返回
│    │    派了个后台任务：查 F 盘 video
│    │        └─ 交底 ▸                     ▸ 展开：brief 原文
│    │    答复：「我去看看」
│    │
│    └─ 后台那边
│         查 F 盘 video · 排队中 → 进行中
│         步骤（3）▸
│         结果 ▸  「F 盘 video 下有 12 个视频」
│
├─ ▸ 14:20  「晚上吃什么」                    已答
│
├─ ▸ 11:05  「今天天气怎么样」                已答
```

**三层折叠**

| 层 | 是什么 | 默认 |
|---|---|---|
| 块 | 一次发话 | 后台还在跑 → 展开；否则折起 |
| 段 | 桌宠这边 / 后台那边 | 展开（内容就几行） |
| 明细 | 模型每轮、工具参数与结果、交底、步骤 | 折起 |

**时间分组**：最外层按天分组——今天 / 昨天 / 更早（更早按月）。分组头显示该组多少块。

**块标题行**：时间 · 你的那句话（截断到一行）· 状态徽标。徽标只有四种：**已答 / 后台运行中 / 已完成 / 失败**。没有后台任务时是"已答"。

徽标怎么定：一轮里有 `reply` 记录 → 「已答」；有后台任务且还有没到终态的 → 「后台运行中」；任务全到终态 → 「已完成」（其中有失败的任务则「失败」）；既没有 `reply` 也没有任务 → 「失败」（前台这一轮没答上来）。

### 4.2 记录形态

**新增一个分类 `model`（模型的一轮往返）**

```js
{ kind: 'model', role: 'assistant', text: '模型这一轮说的话', at,
  meta: { layer: 'interaction', index: 1, model: 'MiniMax-M2' } }
```

- 只给**交互层**记（执行层的工具调用已经有 `step` 记录，不再重复记正文）。
- 加进 `CHAT_KIND` 与 `CHAT_KIND_LIMITS`（上限 200，与 `step` 同量级）。
- **不进 `CHAT_KIND_FOR_LAYER`**：两层模型都看不见它——它是给人看的。

**只记有正文的轮。** 工具调用轮模型通常没有正文（它只给 tool_calls），那种轮由 `step` / `dispatch` 记录表达，不另记一条 `model`。否则页面上会出现一串空条目。

**轮数记在 `reply` 的 meta 里**（`meta.rounds`），不靠数 `model` 记录条数——数条数会把"模型不支持工具、退回普通对话"那种轮算漏。页面上的「问模型 MiniMax-M2 · 3 轮」读的是它。模型名也放这儿（`meta.model`）。

**扩展现有分类的 meta**

| 分类 | 新增字段 | 为什么 |
|---|---|---|
| `dispatch` | `brief`（交底原文）、`layer: 'interaction'` | 派单时交底的三样东西里，brief 是唯一没记的 |
| `step` | `layer: 'interaction' \| 'execution'` | 区分交互层的快工具与执行层的工具；执行层的旧记录没有这个字段，按 `execution` 兜底 |
| `reply` | `taskId`、`layer: 'execution'` | 后台完成时桌宠说的话，靠它归回原来那一块 |

**不新增的**

- 交互层的**任务管理工具**（`task.submit` / `task.list` / `task.cancel` / `task.delete` / `task.steer`）不记成 `step`——它们已经有 `dispatch` 记录，重复记两份会让"桌宠这边"出现两行说同一件事的话。
- 交互层的**快工具**（`clock.now` / `clipboard.read` / `fs.read` / `fs.list`）记成 `step` + `layer: 'interaction'`。

### 4.3 一次发话的归属规则

归属是纯逻辑，落在 `plugins/chat-history/pages/turns.js`（不碰 DOM，能在普通 node 里测）。

1. **切轮次**：一条 `user` 记录开一轮；桌宠**主动**说的话（`proactive`）也开一轮（用户没发话，标题就用桌宠那句），**它的过程记录也归这一轮**。一条 `user` 之后、下一个 `user` 之前产生的记录，都属于这一轮。
2. **收后台任务**：有 `taskId` 的 `task` / `step` / `approval` / `reply` 合成一个"后台任务"。任务归属到**派单它的那一轮**——找带这个 `taskId` 的 `dispatch` 记录，它落在哪一轮，任务就在哪一轮。
3. **找不到派单的任务**（旧数据、接线完成前的记录）：自己成一块，标题取任务标题，归到它自己开始的那天。
4. **交互层的记录**（`model`、交互层的 `step`、`dispatch`、`reply`）按时间挂到它所在的那一轮。**前台过程记录**（`model`、不带任务号的 `step`、以及 `dispatch`）默认留在它所在的那一轮；只有**主动搭话自己那一轮**的过程记录挪到主动搭话那块——从主动答复往前找那串连续的过程记录（遇到用户发话或另一条答复就停），按答复带的轮数（`meta.rounds`）切出最后几轮，那是主动搭话自己跑的；更早的属于上一轮（那一轮可能还没答上来），留在原地。其派出去的后台任务跟着它一起挪。答复带不出轮数时，那串记录整串归主动搭话。孤儿记录（没有对应的那句话）不参与归位，它自己那一块与「没有对应的那句话」的标都留着。
5. **一轮里没有交互层记录也没有后台任务**（比如模型直接答了）：那一轮就只显示"你说了什么 + 问模型 X · N 轮 + 答复"。
6. **一个任务号有多条 `dispatch`**（派单一条，后来的停/追加要求又一条，都带它）：任务归到**最早**那条（派单那一轮）——任务是那一轮造出来的。后来的 `dispatch` 记录留在**它们各自所在的那一轮**：用户后来又说话要"停掉它"，那一轮就该看得见这个动作。
7. **孤儿记录**（`user` 被 40 条上限砍掉了，`model` / `dispatch` 还在）：没有锚点的记录**自成一块**，标题取该块里第一条有正文的记录（桌宠的话，或派单动作），并标成"没有对应的那句话"。**不丢**——丢了就再也找不回来。

### 4.4 实时更新与展开状态

现在的 `captureView` / `restoreView` 只记住任务卡里展开的步骤。新的展开状态有三层（块 id、明细 id），重画时一起记住：

- 重画前的展开状态 → 重画后恢复；
- 用户手动改过展开状态的块，**下次重画不再被默认值覆盖**（默认展开只作用于"用户没碰过的块"）；
- **新的在前**（块按时间倒序）。所以新记录进来是在**上面**，不是下面——现在那句"贴着底部就跟着往下走"要改成"他在看最新就保持不动，往下滚了就别拽他"。
- **滚动定位**：本来停在最新一条时视口不动（新记录直接出现在眼前）；往下滚了才锚住他正在读的那条。

### 4.5 界面文案

页面上只出现用户看得懂的话：

| 内部 | 页面上的话 |
|---|---|
| `model` 记录 | 「问模型 MiniMax-M2 · 3 轮」/ 展开后每轮「第 1 轮：…」 |
| 交互层 `step` | 「调了一次剪贴板」/「看了目录 src/」 |
| `dispatch`（`task.submit`） | 「派了个后台任务：查 F 盘 video」 |
| `dispatch`（`task.list`） | 「看了看后台任务」 |
| `dispatch`（`task.cancel`） | 「停掉了任务：{title}」 |
| `dispatch`（`task.delete`） | 「归档了任务：{title}」 |
| `dispatch`（`task.steer`） | 「给任务追加了一句要求」 |
| `dispatch.meta.brief` | 「交底」 |
| 执行层 `task` / `step` | 「查 F 盘 video · 排队中 → 进行中」/「步骤（3）」 |
| `reply`（执行层） | 一条可折叠的明细：摘要写「结果」，正文是那句话 |

五个任务管理工具各有一条 `dispatch` 记录，页面按 `meta.tool` 映射成上面的话；**不认识的工具直接显示 `meta.action` 原文**（别把工具名甩给用户看）。

**「问模型 X · N 轮」那行有没有得展开，看情况**：单轮对话（那一轮的正文就是答复正文）或退回普通对话那一轮（没记模型原话）都没有可展开的轮次，这时只留那一句，不给一个点开是空的盒子。只要这一轮有前台答复，那一行就画出来——模型名与轮数从答复上取。旧记录两样都没有（既没记模型原话，答复上也没带轮数与模型名），那一行就不画。

**`taskId` 不上界面。** 停掉与归档那两句用**任务标题**指认任务，不显示 `t-1` 这种内部编号——
用户看到的是一个他自己不认识的编号，既没有信息量，也是把内部结构甩到了界面上。
取不到标题时退成「停掉了那个后台任务」。

## 5. 依赖与顺序

```
① 两层接线（按已有计划做，本项目一并做掉）
   docs/superpowers/plans/2026-11-08-two-layer-agent.md 的 Task 4
   ——前台走交互层、后台走执行层；完成通知写成 reply 记录（该计划已含）
   **加一条**：完成的 reply 记录必须带 meta: { taskId, layer: 'execution' }。
   该计划写的完成记录不带 taskId，而归属算法要靠它把结果归回原来那一块；
   tasks.js 的 notify 载荷本身也不带 taskId，要一并带上。
        ↓
② 补记（本项目新增）
   loop 暴露每轮的模型正文 → 交互层记 model 记录
   交互层的快工具 → step 记录（layer=interaction）
   派单记录带上 brief
        ↓
③ 页面重设计（本项目主体）
   turns.js 归属算法 → history.js 分块渲染 → history.html 样式
```

**为什么 ① 必须先做**：不接线的话前台不走交互层，`model` 记录一条都不会有，"桌宠这边"永远是空的。

## 6. 测试策略

**单元（`node --test`，不碰 electron）**

- `turns.js` 的归属算法：派单的任务回到原来那一轮；一个任务号有多条 `dispatch` 时归到最早那条；找不到派单的任务自成一块；主动搭话自己开一轮；`user` 被砍掉后的孤儿记录自成一块；一轮里的交互层记录按时间归位。
- 徽标：有 reply 是「已答」；有任务在跑是「后台运行中」；任务全完是「已完成」；既没 reply 也没任务是「失败」。
- 记录形态：`dispatch` 带 brief；`model` 记录进 `CHAT_KIND` 后**不会被降级成 reply**（降级了就会混进模型上下文）；`model` 不进任何一层的模型上下文。

**e2e（playwright）**

- 页面出现块结构：一块里有"桌宠这边"与"后台那边"两段。
- 交底默认折起，展开看得到 brief 原文。
- 后台任务完成后，结果出现在**原来那一块**里。
- 新记录进来时，用户手动展开的东西不会被收起。

## 7. 未决与风险

- **旧记录怎么显示**：接线完成前的记录没有 `dispatch`，任务按 4.3 第 3 条自成一块。页面上会有"一句话 + 一个独立任务块"的样子。**接受**——历史数据不值得为了好看再洗一遍。
- **一轮里派多个任务**：一个 `dispatch` 一个 `taskId`，任务各自成卡，都在这一轮的"后台那边"。**接受**。
- **交互层的中间正文很长**：`model` 记录的 text 会被 `capMeta`/正文截断砍到 2000 字。**接受**——正文只是给人看个大概。
