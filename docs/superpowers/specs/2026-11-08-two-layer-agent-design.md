# 桌宠的双层 agent · 设计

> 日期：2026-11-08
> 状态：待评审
> 范围：`src/main/assistant/` 新增 `layer/` 子系统；`agent/` 增补 steer 与 dispatch 记录；`src/shared/assistant.js` 契约扩展
> 取代：`2026-11-07-agent-runtime-design.md` 的 **§3.1（两种对话后端）** 与 **§7（后台任务运行时）的角色划分**——那两节把「对话」和「任务」当成同一个后端的两种模式，本设计把它们拆成两个角色。

---

## 1. 背景

### 1.1 现在「奇怪」在哪

不是玄学，是三处具体的结构问题。

**（1）对话和任务是同一条通道。**
`assistant/index.js` 的 `runChat` 一轮 = 一次前台对话；agent 的整个多步循环（`chat/agent.js` → `agent/loop.js`）就塞在里面。气泡从开始到结束被这一轮占住，几十秒里用户只看到一只空 bubble。`chat/ack.js` 的「先应一声」就是给这个矛盾打的补丁——它承认了这段时间是哑的。

**（2）长任务的结果会因为用户又说了句话而消失。**
`runChat` 里 `const token = ++chatSeq`。用户在任务跑着的时候又发一句 → `chatSeq` 递增 → 前一轮回来时 `token !== chatSeq` → 走「这一轮被新的对话取代了」那条路：**结果不写进历史、气泡被取消**。但那一轮的工具副作用（文件写了、命令跑了）**已经发生了**。

这条是最硬的问题：不是「等待太久」，是**结果会丢**。

**（3）任务一多，用户看不见也管不着。**
任务本体只在运行时内存里，界面上一览无余。用户想「停掉刚才那个」，只能靠记忆和猜。

### 1.2 已有地基

L0–L3 已经把「执行层」的三大件做出来了：

| 已有 | 位置 | 在新设计里的角色 |
|---|---|---|
| 队列 / 并发 / 取消 | `agent/runtime.js` | 执行层的生命周期 |
| 审批闸门（三档策略、永久放行） | `agent/approval.js` | 执行层的权限 |
| 分类记录 + **只有 user/reply 进模型上下文** | `agent/record.js`、`chat/prompt.js` | 两层上下文隔离的地基 |

缺的不是零件，是**角色划分**：前台对话和后台任务还共用同一个后端入口（`llm.backend` 全局开关）。

## 2. 目标与非目标

### 2.1 目标

1. 前台那一轮**不含慢工具**：回复是秒级的，不被后台任务占住气泡。
2. 长任务与对话**互不打断**：用户在任何时刻说话都不会让正在跑的任务消失。
3. 交互层能**派单、查看、停止、删除、追加指令**——用嘴管理后台任务，不做新界面。
4. 两层的上下文**互不污染**：执行层跑十步不会把交互层的对话冲垮。

### 2.2 非目标

| 不做 | 理由 |
|---|---|
| 任务列表 UI | 交互层本身就是任务管理的界面（「停掉刚才那个」→ 一次工具调用）。真需要界面时再说 |
| 执行层用不同的模型 / 配置 | 本期共用一份 LLM 配置。真要分开（例如长任务用便宜模型）再说 |
| 多 agent 并行、任务 DAG | `maxConcurrent` 已有，够用 |
| 任务持久化与恢复 | 沿用旧规格 §7.4：跑着的 shell 子进程早就死了，假装能恢复是自欺欺人 |
| steer 的中途改写任务定义 | steer 只是**追加一句**，不改任务目标本身 |
| L4（harness）、L5（聊天记录插件） | 照旧排在后面，与本设计不冲突 |

## 3. 两个角色

| | **交互层**（前台） | **执行层**（后台） |
|---|---|---|
| 唯一职责 | 跟用户说话 | 干活 |
| 模型轮次 | ≤ 3（`maxSteps=3`） | ≤ `agent.maxSteps`（默认 20） |
| 快工具 | 白名单，**合计最多 1 次** | 全部工具 |
| 任务管理工具 | 5 个，**不限次数** | — |
| 审批 | **不经过闸门**（全是瞬时安全操作） | 走现有闸门 |
| 看得见的记录 | `user` / `reply` / `dispatch` | `user` / `reply`（自己那份简报） |
| 谁说话 | 桌宠的每一次回话 | 不直接说话，只产出结果 |

**一句话：交互层是唯一跟用户说话的，执行层只产出结果。**

## 4. 交互层

### 4.1 工具集

全部瞬时、全部免审批——这是它能保持秒级的**唯一原因**。

| 工具 | 作用 | 参数 | 返回 |
|---|---|---|---|
| `task.submit` | 派一个后台任务 | `{ title, brief }` | `{ taskId }` |
| `task.list` | 列出任务 | — | `[{ taskId, title, status, lastStep, result, elapsedMs }]` |
| `task.cancel` | 停掉正在跑的任务 | `{ taskId }` | `{ ok }` |
| `task.delete` | 把一个**已结束**的任务从列表里归档 | `{ taskId }` | `{ ok }` |
| `task.steer` | 给正在跑的任务追加一句要求 | `{ taskId, note }` | `{ ok }` |

**快工具白名单**（`risk: read`，只读、毫秒级）：

| 工具 | 说明 |
|---|---|
| `clock.now` | 当前时间 |
| `clipboard.read` | 读剪贴板 |
| `fs.read` | 读单个文件 |
| `fs.list` | 列一层目录 |

### 4.2 「最多一次快工具」怎么强制

**由工具执行器强制，不靠提示词自觉。**

- 快工具的执行器带一个计数器：本次对话里**尝试**过 1 次之后，再调用就返回
  「这一轮只能用一次快工具，请直接给出答复」。
- **配额按尝试计数，失败也算用掉**——失败之后的唯一出路是转派（§4.6），不是重试。
- 计数是**每次交互层对话一轮**重置的（不是全局）。
- **任务管理工具不受这个配额限制**——否则交互层既不能派单也不能查任务。
  （它们仍然受轮次上限约束。）

轮次上限 `maxSteps=3`：典型流程都能走完——

| 场景 | 轮次 |
|---|---|
| 提示词里已有答案（「现在几点」） | 1 |
| 快工具答（「剪贴板里是什么」） | 2 |
| 派单（「F 盘 video 下有什么」） | 2（第 1 轮 `task.submit`，第 2 轮给答复） |
| 快工具失败 → 转派 | 3（第 1 轮快工具失败、第 2 轮 `task.submit`、第 3 轮给答复） |
| 查 + 停（「第二个停了」） | 3（`task.list` → `task.cancel` → 答复） |

第 3 轮还不给答复就按 `fallbackText` 收尾（沿用 `chat/agent.js` 的做法）。

### 4.3 提示词预置（每轮重建，不花工具调用）

交互层的系统提示词每轮重建，尾部拼一段**实时状态**：

```
现在是 2026-11-08 14:32（Asia/Shanghai）。
后台正在跑 2 个任务，排队 0 个。
对话模式：可以派单。
```

所以「现在几点」「还有几个任务在跑」**不需要任何工具调用**。当前时间也能省掉一次快工具。

### 4.4 派单要带三样东西

`task.submit` 的参数不只是提示词，还有两份上下文：

1. **用户原话**（逐字，来自本轮的 user 消息）
2. **交互层的理解**（`title` + `brief`：想干什么、要什么结果、有什么约束）
3. **相关历史**：执行层自己再读最近几条 `user`/`reply`（沿用 `agent/tasks.js` 里 `getMessages` 的做法）

只给 1 → 执行层不知道约束；只给 2 → 细节全丢。

### 4.5 分派判断

**由交互层模型自己判断**（不给「去做」这类关键词，也不做界面开关之外的显式触发）。

判断依据写在交互层的提示词里：

- 能自己答的（闲聊、它知道的事、提示词预置的实时状态）→ 直接答
- 需要查本机 / 要动手 / 要跑一会儿的 → 派单
- **快工具失败 → 必须转派后台任务**（本轮唯一的降级路径）

派单前交互层**先自己答一次**，不行才派——避免闲聊也被派单。

### 4.6 降级

| 情况 | 处理 |
|---|---|
| 快工具失败 | 不重试。错误喂回模型，提示词要求它转派 `task.submit` |
| 模型判定该派单但没派 | 桌宠就直接回答（可能不准）。派单记录可查，用户能看出它没派 |
| `task.submit` 失败（运行时不认） | 交互层如实说「派不出去」，不假装在办 |

## 5. 执行层

### 5.1 现有部分

执行层 = 现有的 agent 后端（`chat/agent.js` + `agent/loop.js`）+ 运行时 + 闸门，**基本不动**。变的只有两点：多一个 steer 入口，任务上下文来自派单而不是前台对话。

### 5.2 steer：给跑着的任务追加一句

`runtime.steer(taskId, note)` 把追加指令排进**该任务自己的**指令队列。

agent 循环**每轮开头**检查一次队列：有新指令就作为一条 `role:'user'` 消息插进上下文，然后继续跑。

```
用户 → 交互层 → task.steer('顺便也看看 D 盘')
                    ↓
              执行层当前这一步做完 → 下一轮开头读到新指令 → 继续跑
```

规则：

- 注入点是**步骤边界**，不是任意时刻——正在执行的工具调用不被打断。
- 任务被取消时，指令队列作废。
- steer 的内容不进执行层的「简报」，只作为追加消息。

### 5.3 完成通知

执行层跑完 → 一条**不打断**的完成消息（气泡 + 朗读 + 情绪）。

- 不带 `interrupt`：当前正在进行的对话或正在显示的聊天气泡会把它**排队**（`bubble.js` 的 `show` 已经这么处理），不抢气泡。
- 审批气泡挂着时同样排队——用户正在做决定，不能顶掉。

**开工一句**：派单的同时，交互层已经跟用户说了「我去看看」。所以后台**不需要**再单独发开工通知（否则说两遍）。

## 6. 上下文与记录：按层分流

现有的规则是「只有 `user`/`reply` 进模型上下文」（旧规格 §4.3）。现在多一个维度：**哪一层**。

| kind | 交互层 | 执行层 | 人（记录界面） |
|---|---|---|---|
| `user` | ✔ | ✔（自己的简报 + 派单那一刻的历史快照） | ✔ |
| `reply` | ✔ | ✔ | ✔ |
| **`dispatch`（新增）** | ✔ | ✘ | ✔ |
| `task` / `step` / `approval` | ✘ | ✘ | ✔ |

**`dispatch` 是新分类**：交互层的一次任务管理工具调用（派单 / 查看 / 停止 / 删除 / 追加指令）及其结果摘要。

它必须让交互层在后续轮次看得见——否则桌宠下一句又派一遍单，用户会觉得「怎么一直在重复」。

它**不能**进执行层的上下文：执行层不需要知道「用户还派了别的任务」。

> 执行层看到的 `reply` 里可能混着交互层说的「我去看看」这类话——无害（那也是助手自己的话），但执行层应该**以派单简报为准**，简报里写清楚了要干什么。

### 6.1 派单去重

交互层看得见自己派过什么（`dispatch` 记录），所以「不要重复派同一个单」是它自己能判断的事——提示词里写清楚，代码不强制。

### 6.2 删除任务 = 归档

`task.delete` **只影响可见性，不抹记录**：

- 归档后的任务不再出现在 `task.list`，也不计入提示词预置的「正在跑 N 个」。
- 记录条目（`task`/`step`/`approval`/`dispatch`）**保留**——那些是安全审计，抹掉不好。

正在跑的任务不能删——要先 `task.cancel`。

## 7. 数据流与时序

### 7.1 一次「F 盘 video 下有什么」

```
用户
 └→ 交互层（0~3 次模型调用，秒级）
      ├─ 能自己答 → 直接答 → 结束
      └─ 要动手 → task.submit { title, brief } + 用户原话 + 最近历史
                  → 回一句「我去看看」
                  ↓
              执行层在后台跑（N 次模型调用 + 工具 + 可能等你点头）
                  ↓
              完成通知（气泡 + 朗读，排队不打断）
```

### 7.2 用户在这期间又说话

```
用户 → 交互层（第二轮对话，正常跑）
       执行层的任务：不受影响，继续跑
```

**这正是现在会丢结果的那条 bug。** 修法：前台对话与后台任务彻底分开，各自的 `token`/序号互不干涉。

### 7.3 记录流

| 时机 | 写入的 kind |
|---|---|
| 用户说话 | `user` |
| 交互层调任务管理工具 | `dispatch` |
| 交互层给答复 | `reply` |
| 执行层任务状态变化 | `task` |
| 执行层的一次工具调用 | `step` |
| 执行层的审批请求与决议 | `approval` |
| 执行层完成 | `reply`（桌宠说出去的话，交互层下一轮记得） |

## 8. 错误处理与边界

| 情况 | 处理 |
|---|---|
| 快工具失败 | 错误喂回模型 → 转派后台（§4.6） |
| 交互层模型调用报错 | 沿用 `LLM_ERRORS` 分类；气泡说清原因；**不**派单 |
| 交互层超出 `maxSteps=3` | `fallbackText` 收尾，不空着 |
| 派单成功但执行层立刻失败 | 完成通知说清失败原因；记录里留 `step` 的 error |
| 执行层跑到一半用户又说话 | 互不影响（§7.2） |
| steer 到达时任务刚好结束 | 指令丢弃（不报错） |
| steer 到达时任务已被取消 | 指令作废，返回 `{ ok: false }` |
| 应用退出 | `runtime.stop()` 取消所有任务；挂起的 steer 队列作废 |
| 桌宠隐藏时任务完成 | 完成通知照常（气泡是独立窗口）；但桌宠的表情看不见，所以记录里必须有 |

## 9. 持久化

沿用 `assistant.json`，加两个字段：

```js
assistant.json
  llm.backend            // 'chat' | 'agent'  → 退役（见 §10.3）
  agent.dispatch         // 'auto' | 'off'    // 能不能派单（默认 'auto'）
  agent.maxConcurrent    // 已有
  agent.maxSteps         // 已有
  agent.approval.*       // 已有
  chat.messages[]        // 记录，多了 dispatch 这一类
```

**任务本体不持久化**（沿用旧规格 §7.4）。`dispatch` 记录持久化——它是聊天记录的一部分。

### 10.3 退役

`llm.backend` 的 `'agent'` 取值退役。

- 它原来的意思是「用多步循环的那个后端」，现在前台恒定是交互层，没有选择余地。
- 取而代之的是 `agent.dispatch`：`'auto'` 允许派单，`'off'` 只聊天 + 快工具。
- **迁移**：读到 `llm.backend === 'agent'` 时按 `dispatch: 'auto'` 处理，并把 `backend` 归一为 `'chat'`（写回时）。

## 12. 任务拆分（概览）

详细实施计划由 `writing-plans` 产出。这里的编号是执行顺序。

| # | 任务 | 依赖 | 验收 |
|---|---|---|---|
| T1 | 记录加 `dispatch` kind + **按层过滤** | — | 交互层看得见 dispatch，执行层看不见；task/step/approval 两层都看不见 |
| T2 | 交互层后端（工具白名单 + 配额 + 预置提示词） | T1 | 快工具只能用一次；轮次 ≤ 3；提示词含时间与任务计数 |
| T3 | 五个任务管理工具 | T2 | submit/list/cancel/delete/steer 语义正确 |
| T4 | 两层接线（前台交互层、后台执行层） | T2、T3 | **结果不再被新对话吞掉**（回归测试绿） |
| T5 | steer（运行时 + 循环注入） | T4 | 追加指令在下一个步骤边界生效 |
| T6 | 设置与迁移（`agent.dispatch`，退役 `llm.backend` 的 agent） | T4 | 老配置读起来是 `dispatch: 'auto'` |

L4（harness）、L5（聊天记录插件）照旧排在后面，与本设计不冲突。

## 13. 风险与未决

| 风险 | 影响 | 应对 |
|---|---|---|
| **交互层该派不派** | 模型不派单，用户以为程序没反应 | 提示词明确「凡是查本机/动手/耗时一律派单」；快工具失败强制转派；`dispatch` 记录可查 |
| **交互层不该派乱派** | 闲聊也派单，桌宠神经质 | 派单前先自己答一次；快工具覆盖大部分简单场景；`agent.dispatch: 'off'` 可关 |
| **两套提示词互相干扰** | 层一的 brief 写歪，层二跑偏 | `brief` 与用户原话一起传；层二拿得到原话，brief 写歪也还能自纠 |
| **交互层多花一次模型往返** | 派单类的对话比现在慢 1~2 秒 | 这是刻意的：省下的是几十秒的等待，不是几秒 |
| 跑通的总时长变长 | 多一次交互层调用 | 派单类任务总时长 +1~2 次模型往返；可接受 |

### 未决（本期按默认处理）

| 问题 | 本期默认 |
|---|---|
| 交互层用哪个模型 | **与执行层共用同一份 LLM 配置**（同一个 model 字段；`maxTokens` 各自 clamp：交互层按普通对话，执行层按 agent 的下限 2048） |
| 交互层能不能同时派多个任务 | 能——`maxConcurrent` 已经控制并发；交互层一次派多个是它自己的决定，宿主持「不同时超过上限」 |
| 任务要不要归档而不是删 | 归档（保留记录，只是不出现在列表里），见 §6.2 |
